# 005 — Intent and visible outcomes (0.3.1)

## Evidence

A controlled native reproduction returned `A Fenwick tree supports prefix sums.` from the provider. The old controller replaced it with a zero-file/zero-check report. Every normal submission used the coding system prompt and tool schemas, copied the project and validated completion. Empty text was accepted. Follow-ups carried image references and sometimes a proposal, but omitted the previous explanation. Interrupted streams were detected by the provider but omitted from bounded response recovery.

## Decisions

- Intent is independent of model tier and permission mode. Rust persists Converse, Inspect or Execute. Auto first considers explicit prohibitions and action/question structure, then prior task context and project references. For ambiguous wording, one local, tool-free classification can resolve intent. Invalid/unavailable classification retains conservative conversation. Ask forbids edits; Act still requires an actionable request. Image attachment alone never authorizes edits.
- One base/security prompt composes with a short intent layer. Conversation sends no tool schemas, needs no coding-compatibility probe, and creates no snapshot or source excerpts. Inspect exposes read and approved diagnostic recipes. Execute exposes edits and diagnostics. Dispatch independently rejects capabilities outside intent; hiding schemas is not a security boundary.
- Inspect cannot use editing tools or Apply, even with Project permissions. Test/lint recipes require the existing explicit host-code consent and run in a private copy. Scripts are **not sandboxed** and can write files; any private-copy source changes remain quarantined from Apply. We do not claim read-only host execution. Non-fixing lint/test selection is not proof that arbitrary project code is pure.
- Explicit follow-ups create a new attempt linked to the prior task. A bounded 8 KiB context contains the previous request/answer and relevant evidence. No recursive raw transcript is retained, and old grants do not become new grants. Execute can continue a pending proposal rather than replaying its edits. Inspection does not take ownership of an existing proposal.
- Existing persisted lifecycle names remain compatible. `transition` records legal edges and diagnostics for unexpected edges. Normal flow is queued → preparing → running; running may enter routing, waiting_approval or validating and resume. Final states are review_ready, failed, escalation_ready, cancelled or interrupted. Cancellation publishes Stopping immediately. Restart never resumes commands.
- Terminal publication belongs to `run_task` after cleanup, not the final model message. `TaskResult` contains task/intent/status, visible answer, changed files, recorded validations, warnings, failure and next actions. Startup interruptions also receive a result. Task-body panics become explicit failures; failed final persistence still notifies the current window. Complete process/OS/storage failure cannot guarantee delivery to a closed renderer; restart reconciliation remains necessary.
- Empty/whitespace-only responses and interrupted/malformed streams receive one bounded retry per model stage before escalation. Partial tool calls never execute. Failed inspection checks are reportable evidence. Execute validation continues the bounded recovery/escalation loop. Existing total turn/tool/command/time limits and repeated-action detection remain authoritative.
- Fast → Balanced → Strong retains the same task/copy/evidence/budgets. Strong retains calibration and consent gates. Exhaustion offers the existing offline Codex package with an investigation summary; no paid/cloud work is dispatched. Continuation records include the interaction constraint.
- Conversational reports are preserved. Execution summaries combine an explanation with recorded file/check evidence; sentences claiming test/check results are omitted from generated explanation so fabricated statistics do not replace recorded checks. Original model notes remain explicitly unverified in Activity.
- Frontend results are separate from activity. A terminal task with no answer displays a fallback, Retry and technical details. Copy diagnostics uses allowlisted version/OS/model identity, intent, status, failure category, counters and transitions, excluding prompts, event prose, source, paths, custom model names and images.

## Limits and extension points

Natural-language routing is fallible; Ask and native permissions remain the hard controls. Compact context can omit older evidence; models must re-read current hashes before edits. Conversation still belongs to an opened project in this release. Responses are assembled after bounded inference rather than token-streamed into the renderer. No new browser operator, MCP client, Windows/Office control, scheduler, training or multi-agent subsystem is introduced. Future capabilities must declare their intent eligibility, obey native permission/cancellation boundaries and return structured observations/failures.
